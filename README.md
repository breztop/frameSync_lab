# Frame Sync Lab

当前版本：**v0.1.1**。

用于 BreFlow source → sink 同源画面可见延迟测试的离线 Godot 4.7 轻量 2D 项目。支持 Windows、Linux、macOS 的 x64 / ARM64 导出。默认 1152×648 客户区、Compatibility 渲染器、目标 60 FPS、VSync 开启、轻负载背景。继承原项目版本，不需要网络服务。

**当前交付为源码、桌面导出预设与标签发布 CI。此次修改未启动 Godot、执行 CI 或完成新界面的运行/画面/性能验收。** 此工具也不能确定 BreFlow 约 10 秒卡死的根因。

## 使用

在 Godot 中导入 `project.godot`，运行主场景。启动自动开始首轮，前三秒标记为预热。主读数固定在画面垂直中央，计时卡片左右留有边距。顶部只保留标题和按钮，可按 H 隐藏整个工具栏，再按 H 恢复。设置默认收起；打开后为接近全屏的独立面板，返回测试画面后再拍摄。

| 操作 | 按钮 / 快捷键 |
| --- | --- |
| 清空上一轮并新建计时、编号、统计 | 新一轮 / N |
| 停止本轮记录 | 结束 / Space |
| 停止本轮并后台导出 | 结束并导出 / E |
| 显示或隐藏设置 | 设置按钮 / Tab（编辑输入框时也有效） |
| 关闭设置或 About | 返回测试 / Esc |
| 使用说明与许可 | 关于 |
| 隐藏 / 恢复整个顶部工具栏 | 隐藏按钮 / H |
| 打开最近一次导出的日志目录 | 提示中的“打开日志” / 顶部“打开日志” |
| 查看结果文件 | 打开记录目录 |

设置分为“画面与运动”“窗口与帧率”“测试环境记录”三个标签页，每项直接显示中文说明。当前背景不适用的运动选项会禁用。面板内 N / Space / E 不触发主画面操作，输入框可正常编辑；Tab 专用于开关设置。**新一轮会清空旧数据，需保留的轮次请先导出。** 导出时禁止新建轮次，避免并发修改记录；成功、失败及操作提示显示 5 秒后自动隐藏。导出成功提示提供“打开日志”按钮，打开该次导出目录；提示消失后仍可通过顶部“打开日志”访问最近结果。记录到 200 万条时自动停止，防止内存无限增长。关闭程序不自动保存；导出过程中关闭会等待写入完成。

设置包括三种背景、低/中/高复杂度、速度、细节密度、动态元素数量、固定种子、客户区尺寸、VSync 和目标 FPS。复杂度档位会设置密度与数量，之后仍可分别调整；导出保存实际值。已移除极限压力模式和噪声覆盖选项。

典型桌面包含移动窗口图块、滚动小字、平移的程序生成图案；无需外部图片。该模式最多绘制 12 个窗口，高复杂度模式最多 4096 个批量绘制图元。纹理由简单着色器计算。固定种子与时间使运动可重复；跨 GPU 的浮点结果不保证逐像素相同。

请填写显示刷新率、机器/显示器、采集分辨率、编码码率、sink 预览尺寸和备注。默认采集分辨率 1920×1080、编码码率 20,000 kbps，这些仅为记录字段，不会修改 BreFlow。窗口大小、系统桌面大小、采集大小、sink 大小分别记录。操作系统可能限制大窗口，报告中的 `client_width/height` 才是实际客户区。非 16:9 窗口保持比例并留边。

## 导出与统计定义

默认记录目录为 `%APPDATA%\Godot\app_userdata\frameSync_lab\exports`；程序的“打开记录目录”会使用真实 `user://` 路径。每次导出新建独立目录，不覆盖旧结果。

| 文件 | 内容 |
| --- | --- |
| `frames.csv` | 轮次、绝对单调微秒、经过微秒、更新编号、间隔微秒、稳定样本标志、配置段编号 |
| `report.json` | 初始配置、所有事件及配置快照、全量/稳定/按段统计、样本数、统计口径 |

时间使用 `Time.get_ticks_usec()`，每次 `_process()` 只采样一次，再更新时间、编号与背景。编号代表应用更新，不保证每个编号已经呈现或被采集。第一条记录间隔为 0（无前驱），不纳入间隔统计。长帧后直接显示实际经过时间，不补播历史画面。轮次 ID 的日期仅用于命名，计量不使用墙上时钟。

实时 dt 和最近五秒最大间隔每帧刷新；五秒窗口实测更新率每 250 ms 刷新。平均更新率为有效间隔数 / 有效间隔总时长。P50/P95/P99 使用 nearest-rank：排序后取 `ceil(N×p)` 项；阈值次数严格按 `>33.3`、`>100`、`>200 ms` 统计，不能转换为丢包/显示丢帧数。

原始间隔全部保留，`all_intervals` 包含预热与切换长帧。`stable_intervals` 排除首三秒以及设置、窗口、设置面板或 About 显示切换后一秒；间隔两端都必须越过排除边界。`events` 给出边界、事件时间、下一更新编号和配置快照，`stable_by_segment` 分段报告，避免将不同模式当作同一配置。持续负载造成的长帧不会自动排除。不要只看稳定统计而忽略全量和事件。

每帧仅向内存数组追加数据；CSV 写入和分位数排序在结束后的后台线程完成。无运行时外部资产加载；固定场景和着色器在首次预热之前加载。引擎级场景/脚本损坏仍需查看 Godot 错误输出，不能保证损坏的安装包能正常启动。

## Windows 导出

1. 使用与项目匹配的 Godot 4.7，安装同版本 Windows 导出模板。
2. 创建项目下 `build` 文件夹，打开“项目 → 导出”。
3. 选择 `Windows x64` 或 `Windows ARM64` 预设，导出 Release 到对应的 build 子目录。
4. Windows 预设按所选架构导出、嵌入 PCK，无控制台包装器。将 exe 拷贝到目标 Windows 机器后离线运行验收。

本轮遵照“不运行 Godot”的要求没有执行上述步骤；导出模板可用性、着色器编译、系统字体回退和 DPI 布局均待实机验证。

已完成的非引擎检查：资源路径和场景节点引用无缺失；Python CSV 复核器通过空样本、分位数、严格阈值边界、合成记录一致性及损坏统计拒绝检查。本次使用 gdtoolkit 完成 GDScript 文法检查，并核对 YAML 语法、六个导出预设映射、资源与节点引用。引擎类型检查、着色器编译和实际六平台导出仍未执行。这些检查不构成实际导出文件或游戏运行的测试证据。

## 测量与验收

1. 显示器设为 60 Hz，VSync 开启，选轻负载；填写全部环境字段。隐藏设置后新建轮次，先预热三秒，再连续记录至少 60 秒，然后导出。
2. 分别完成“仅计时程序”和“同时运行 BreFlow source”两轮；避免测试中拖动窗口或修改设置。
3. 初始筛查门槛：稳定区间至少 60 秒、平均 59～61 FPS、P99 ≤33.3 ms、无 >100 ms 间隔。全量长帧也需结合事件检查。
4. 三种背景和三档复杂度逐一切换；测试速度/密度/数量、窗口尺寸、VSync；反复结束、新建、导出，确认不串轮，导出期间窗口可响应。
5. 使用不可写目录或磁盘空间不足环境检查导出失败提示和重试。检查字号、字体等宽、设置滚动、800×450 至 2560×1440 与不同 DPI 下的可读性。
6. 每种模式拍摄至少 30 秒。仅 source 运行一个计时器，sink 显示其传输画面。两块屏幕数字放在相近相对高度和相机同一水平线，使用真实 120/240 FPS、较短曝光录像。
7. 从同一录像帧读取“源端显示时间 − sink 显示时间”，取多个清晰样本，报告分布与异常。数字跳跃时对照 `frames.csv` 中编号和帧间隔。

60 Hz 下正常数字步幅约 16～17 ms；毫秒格式不代表 1 ms 可见精度。240 FPS 录像的约 4.17 ms 采样间隔也不是总误差。滚动快门、曝光和两块显示器都会影响读数。结果是相对源屏幕的可见延迟，不是纯网络 RTT；RTT 请另用 BreConn echo UI。高复杂度画面不能保证编码器实际输出 20 Mbps。

可在导出后独立复核 CSV（不需要 Godot）：

```powershell
python tools/check_export.py "C:\实际记录目录\某轮导出目录"
```

复核工具会重算统计、校验编号和单调时间，并对照 JSON。它通过也不能替代屏幕呈现、GPU 完成时间或 BreFlow 传输验收。

## 标签构建与 GitHub Release

工作流 `.github/workflows/export.yml` **只响应推送的 `v*` 标签**。普通分支推送、PR 都不会构建，也没有手动触发入口。本地创建标签还不够，需要把标签推送到 GitHub。

确认要发布的代码已经提交并推送后，例如：

```powershell
git tag v0.1.1
git push origin v0.1.1
```

这两个命令会为当前提交创建版本并触发公开发布；本文只提供操作示例，没有替你执行。标签需要指向包含工作流及所有项目文件的提交。请勿反复移动或覆盖已发布的标签，更新版本时使用新标签。

构建成功后自动在 [GitHub Releases](https://github.com/breztop/frameSync_lab/releases) 创建下载页，上传平台包及 `SHA256SUMS.txt`。带连字符的标签（如 `v0.1.1-rc.1`）标记为预发布。仓库公开时，大家无需通过 Actions 页面便可下载 Release 附件。

| 平台 | 下载包 | 构建方式 |
| --- | --- | --- |
| Windows x64 / ARM64 | `.7z` | 官方 Release 导出模板 |
| Linux x64 / ARM64 | `.tar.xz` | 官方 Release 导出模板 |

四个 Windows/Linux 产物全部成功才发布。macOS 保留官方模板导出，不额外编译引擎；其导出失败不阻塞其他平台，没有成功生成的 macOS 包不会出现在下载页。macOS 使用 ad-hoc 签名，未做 Apple 公证；Windows 未做发行者签名。当前没有实际运行 CI，不能把配置完成视为六平台构建或运行已经通过。

### 官方模板与高压缩打包

整个流程只用 **一个 Ubuntu runner、一个 job**，顺序完成下载、导入、六个目标的导出、压缩和 Release 发布。Godot 固定为 **4.7-stable**，直接使用同版本官方编辑器和导出模板，**不从源码编译引擎**，不安装 SCons、MSVC 或交叉编译器。

Windows/Linux 四个包必须成功，macOS 两个包可选。导出只包含主场景及其依赖与必要许可文件。官方模板包含通用引擎功能，因此无法达到定制裁剪引擎的最小体积；这里通过精简项目资源和高压缩下载包控制体积，优先保持构建简单。

Windows 使用 7z / LZMA2、`-mx=9`、64 MiB 字典及固实压缩；可用 7-Zip 解压。Linux/macOS 使用 `tar.xz` 与 `xz -9e`，保留执行权限和应用目录结构，解压命令为 `tar -xJf 文件名.tar.xz`。macOS 先展开引擎生成的 ZIP 再压缩为 tar.xz，不把两个压缩包叠在一起。Actions 上传禁用重复压缩。

每份包包含完整项目 `source/`、`LICENSE`、`THIRD_PARTY_NOTICES.txt`、`README.md` 和 `BUILD.txt`。不要从分发包中移除对应源码与许可。正式下载使用 Release 附件，不再传递中间构建产物。实际大小会写入工作流 Summary；尚未获得实测包体积，不能承诺压缩比例。
